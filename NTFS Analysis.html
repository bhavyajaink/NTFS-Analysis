NTFS file system: understand it byte by byte

The hex samples below are generated on this page (small, simplified examples that follow the real NTFS layouts). Click any byte or table row to see the field name, offset and value.

What NTFS is

NTFS (New Technology File System) is the default file system of Windows since Windows NT 3.1 (1993). Think of a file system as a library: the data are the books, and the file system is the catalogue that says where each book is.

NTFS is a journaling file system. It writes changes to a log before applying them, so the system can recover after a crash or power failure, and an investigator gets a history of file activity.

Key features

• Detailed metadata (several timestamps per file) • Journaling ($LogFile and $UsnJrnl) • Permissions (ACLs) and encryption (EFS) • Compression • Very large files and volumes • Better resilience than FAT32

Volume layout

Simplified. The $MFT lives in a reserved zone near the start; $MFTMirr is stored separately so a damaged MFT can be cross-checked.

Three things to remember before reading any hex

• NTFS stores numbers little-endian: 0x1000 as a 4-byte value is 00 10 00 00.
• Times are FILETIME: 100-nanosecond ticks since 1 January 1601 (UTC).
• Names are UTF-16LE: “A” = 41 00.
• Everything is a file, even the file system’s own metadata ($MFT, $LogFile…). That is why we can export and analyze them.

How NTFS finds C:\Users\Ravi\salary.xlsx

  1. Read the boot sector to learn the cluster size, the record size and where the $MFT starts.
  2. Read MFT entry 5, the root folder. Its index ($I30) lists the names inside it.
  3. Look up Users in that index. The entry gives a file reference (for example entry 311). Read MFT entry 311 and open its index.
  4. Repeat for Ravi, then salary.xlsx.
  5. Read the file’s record. If its $DATA attribute is resident, the content is right there. Otherwise decode the data runs to get LCNs, multiply by the cluster size and read those clusters.

This path walk is why several artifacts matter: the index holds names, the MFT holds metadata and locations, and the clusters hold content. Evidence can survive in any one of them after the others are gone.

Resident vs non-resident data

Resident: a small file’s content is stored inside its MFT record (in the $DATA attribute). Even if the clusters are overwritten, a small file or script can still be recovered from the MFT. Non-resident: a larger file; the record only holds “data runs” pointing to clusters on disk.

Alternate Data Streams (ADS)

A file can hold more than one data stream. The main stream is the normal content; extra named streams can hide content without changing the visible file size. Malware uses this. To list streams: dir /r or Get-Item * -Stream *.

Reserved entries

Entries 0–11 are the metafiles above, 12–23 are reserved, and ordinary files start at entry 24. So entry 5 is always the root folder, and a low entry number such as 7 will never be a normal user file.

Partition Boot Sector (first 84 bytes)

The first sector of an NTFS volume describes the geometry and tells the OS where the $MFT starts. Real sectors continue with bootstrap code and end with 55 AA at offset 0x1FE.

Click on any byte.
How to read this sector, step by step

1. Confirm the OEM ID says NTFS and that the last two bytes of the sector are 55 AA.
2. Cluster size = bytes per sector × sectors per cluster.
3. First MFT record = $MFT start cluster × cluster size.
4. Record size comes from “clusters per MFT record”: a negative byte means 2 to the power of its absolute value.
5. If this sector is damaged, NTFS keeps a backup copy in the last sector of the volume, so recovery tools can still find the geometry.

Forensic checks

Compare the boot sector with its backup copy (a mismatch means damage or tampering). Check that the hidden-sectors value equals the partition’s start in the MBR or GPT. Inspect the bootstrap code for anything unusual, since bootkits replace it. Compare total sectors with the partition size.

Fixups: why sector ends look odd

A 1024-byte record spans two 512-byte sectors. To detect half-written (torn) records, NTFS overwrites the last 2 bytes of every sector with the record’s update sequence number (0x0003 in our sample) and stores the original bytes in the update sequence array at offset 0x30. A parser must put the saved bytes back. If a sector end does not match the number, the record is corrupt. MFTECmd does this for you; when reading raw hex, remember that bytes 0x1FE–0x1FF and 0x3FE–0x3FF are not the real data.

Life of a record

EventWhat changes in the MFT
File createdA free entry is chosen, flags = 0x01, attributes are written, and the name is added to the parent’s $I30.
File deletedFlags become 0x00 (0x02 for a folder), the name leaves the parent index, the clusters are cleared in $Bitmap. Attributes and data are normally left untouched.
Entry reusedA new file takes the entry and overwrites the old attributes; the sequence number goes up. The old metadata is gone, so look in $UsnJrnl, $LogFile and $I30 slack.
Folder deletedThe folder’s entry is freed, but its children keep their own records pointing to a parent that no longer exists (orphan files).

File references

2A 00 00 00 00 00 01 00 = entry 0x2A (42) with sequence 1. If the journal and the MFT show the same entry number with different sequence numbers, they describe two different files.

Resident or non-resident?

If the content fits into what remains of the 1024-byte record (roughly 700 bytes or less), $DATA is resident. Larger content becomes non-resident: the record only keeps a run list that tells where the clusters are. A file can switch from resident to non-resident when it grows, and the old resident bytes may linger as slack.

Data run decoder

Run list (hex):

Assumes 4096-byte clusters. Each run starts with one header byte: the low nibble is the number of bytes that hold the run length (in clusters), the high nibble is the number of bytes that hold the start cluster. The start is a signed offset from the previous run (the first run is relative to 0), so a fragment that sits earlier on disk has a negative offset: F0 = −16. A header byte of 0 ends the list. An offset size of 0 means a sparse run (no clusters).

Sizes explained

Allocated size 32,768 = 8 clusters × 4096. Real size 30,517 is what Explorer shows. The difference, 2,251 bytes, is file slack inside the last cluster. Initialized size is how many bytes were really written (sparse or pre-allocated files can have a smaller value).

When one record is not enough

Files with many fragments, many streams or many hard links can overflow the record. NTFS then adds an $ATTRIBUTE_LIST that points to extension records; each extension’s “base record reference” (header offset 0x20) points back to the base record. Tools that ignore this show incomplete files.

Alternate data streams (ADS)

An ADS is simply a second $DATA attribute that has a name (name length above 0). Explorer shows only the unnamed stream’s size, so extra streams are easy to miss. The most common legitimate one is Zone.Identifier, added when a file is downloaded (Mark of the Web):

invoice.pdf:Zone.Identifier
[ZoneTransfer]
ZoneId=3
ReferrerUrl=https://example.com/downloads
HostUrl=https://example.com/files/invoice.pdf

ZoneId 3 means Internet (0 local, 1 intranet, 2 trusted, 4 restricted). It proves a file came from outside and often tells you the URL. MFTECmd shows it in the ZoneIdContents column. Malware can hide payloads in named streams, so list them with dir /r or Get-Item * -Stream *.

Compressed, sparse and encrypted data

Attribute flags 0x0001 (compressed), 0x8000 (sparse) and 0x4000 (encrypted, EFS) change how the clusters must be read. Compressed files have a compression unit size above 0 in the non-resident header; sparse files contain runs with no clusters that read back as zeros; encrypted content cannot be read without the key.

Timestomp detection checklist

  • $SI Created earlier than $FN Created. The strongest simple indicator, because ordinary tools cannot change $FN.
  • Zero sub-second ticks. Real times have a random 100-ns part; many forging tools write whole seconds. Use the checker below. It is a hint, not proof (some sources also produce whole seconds).
  • MFT changed time that does not fit. Many tools cannot set it, so it may show the real moment of tampering.
  • Neighbour check. Entries are usually allocated in order, so a file whose entry number sits among files from 2026 but claims 2021 is odd (entries can be reused, so use it as a pointer only).
  • Impossible times. Dates before the parent folder, the user profile or the Windows install existed.
  • Corroborate. Compare with $UsnJrnl, $LogFile, $I30 copies, Prefetch, Amcache and event logs. A forged time has to fool all of them.

Limits of the journal

  • It is circular. $Max stores the maximum size and the allocation delta; the oldest records are overwritten first, so on a busy system it may cover only hours or days.
  • Records hold only the file name and the parent reference, not the full path. Resolve paths with the MFT (MFTECmd -m $MFT) or the usnjrnl_rewind tool when the entry has been reused.
  • $J is sparse: its logical size is huge, but only the tail holds data. Export it with a tool that handles sparse streams.
  • Attackers can delete it with fsutil usn deletejournal /D C:. A fresh journal ID or a journal that starts suspiciously late is a clue.

$LogFile in detail

$LogFile (entry 2) is a circular transaction log. Before NTFS changes metadata it writes redo data (how to apply the change) and undo data (how to reverse it). After a crash NTFS replays redo for finished transactions and runs undo for unfinished ones. That is why file systems survive power loss.

  • It begins with two restart pages (signature RSTR) followed by record pages (RCRD).
  • Each log record has an LSN (log sequence number). The MFT header field “$LogFile sequence number” links a record to its last logged change.
  • It is small (tens of MB) and overwritten quickly, so it holds minutes to hours of activity. Collect it early.
  • Parse it with LogFileParser or NTFS Log Tracker; reading it by hand is rarely practical.

Directory index entries ($I30)

Each directory keeps a B-tree index of its children in $INDEX_ROOT, $INDEX_ALLOCATION and $BITMAP, together called $I30. Each entry holds the file reference, and a copy of the $FILE_NAME attribute (name, size, timestamps).

Click on any byte.
Why slack matters

When a file is deleted, renamed or moved, its entry is removed from the active index but is not wiped. The bytes can remain in the unused (slack) part of the index buffer, so you can see which files a folder used to contain even when the MFT record has been reused. MFTECmd marks such rows in the From Slack column; FTK Imager shows them with a red cross.

The container: INDX record header

Small folders keep their entries inside $INDEX_ROOT in the MFT record. Larger folders use 4096-byte blocks in $INDEX_ALLOCATION, each starting with this header. The entry sample above would sit right after byte 0x40.

How the index is organised

  • It is a B-tree sorted by file name, case-insensitive (the $UpCase table defines the comparison). $INDEX_ROOT records that the indexed attribute is $FILE_NAME (0x30), the block size (4096) and whether child blocks exist.
  • Entry flag 0x01 means the entry has a child node (its VCN is stored in the last 8 bytes of the entry); 0x02 marks the last entry, which has no name and only ends the list.
  • The entry’s key is a copy of $FILE_NAME, including the four times and sizes. The copy is written when the entry is created or rewritten, so it can differ from the file’s current record.
  • Slack: “index used size” in the node header (0xA0 in our sample) marks where live entries end. Bytes after it up to the end of the block are slack and can hold complete old entries. When a name is deleted or the tree is rebalanced, the entries shift and the old copies stay behind.
What $I30 can prove

A file existed in a folder even after its MFT record was reused. Its former name after a rename. Its times and size as of the last index update. Hidden or system files that a folder listing does not show. Parse it with MFTECmd (From Slack column) or INDXParse.

What deleting a file really does

  1. The name entry is removed from the parent’s $I30 (a copy usually remains in slack).
  2. The MFT record’s in-use flag is cleared (0x01 → 0x00). Attributes, times and data runs are left as they were.
  3. The file’s clusters are cleared in $Bitmap, so they count as free.
  4. $UsnJrnl gets FILE_DELETE | CLOSE and $LogFile logs the transaction.
  5. The data clusters are not erased. They stay until another file is written over them.

Recycle Bin

A normal delete in Explorer does not delete anything yet. Windows moves the file to C:\$Recycle.Bin\<user SID>\, renaming it to $R<random>.ext (the content) and creating $I<same random>.ext (metadata). $Bitmap, bit by bit

$Bitmap holds one bit per cluster; 1 = allocated, 0 = free. The first byte covers clusters 0–7 and bit 0 is the lowest cluster. Edit the bytes to see the map.

Bytes (hex):

To check a deleted file, take each LCN from its data runs and see whether its bit is still 0. If it is, the content has probably not been reused. If it is 1, another file now owns that cluster.

Carving and shadow copies

Carving searches unallocated space for known file headers (for example %PDF, or FF D8 FF for JPEG) and extracts bytes up to a footer or a length, without needing the MFT. Volume Shadow Copies keep older snapshots of the volume, including old MFTs and journals. List them with vssadmin list shadows and analyze them like separate images.

Case A: data theft followed by deletion

  1. MFT: filter In Use = False and extension .xlsx. Find the record for the file and note its entry and sequence numbers.
  2. $UsnJrnl: search the name. Build the sequence (create → rename → delete) and note the times.
  3. Recycle Bin: look for matching $I files in $Recycle.Bin. The deletion time and the user SID identify who deleted it.
  4. $I30: confirm the name survives in the folder index slack.
  5. Content: if resident, read it from the record; otherwise use the data runs and check $Bitmap.

Case B: malware dropped and timestomped

  1. MFT: list executables in temp and user folders. Compare Created0x10 and Created0x30 and flag every file where the $SI time is earlier.
  2. Check sub-second ticks of the suspicious times; whole seconds support the forgery theory.
  3. Look for a Zone.Identifier stream to find the download URL.
  4. $UsnJrnl: the real creation time appears as FILE_CREATE, regardless of what $SI says.
  5. Corroborate with Prefetch, Amcache and event logs, then build the timeline from the trustworthy times.

Case C: hidden data in an alternate stream

  1. In MFTECmd output look at rows where the record has more than one $DATA attribute.
  2. List the stream names with dir /r and extract them with FTK Imager (they appear as file:stream).
  3. $UsnJrnl: look for NAMED_DATA_EXTEND and NAMED_DATA_OVERWRITE on that file to see when the stream was written.
